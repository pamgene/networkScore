Getting started with networkScore

networkScore computes a permutation-test significance score for a condition’s PCSF network – either kinase-only, or paired with sensitivity data (“golden score”). Every network build goes through networkGen (see vignette("networkGen") for how a network is built and its parameters). spec_cutoff, perc_cutoff, b, rank_uka_abs, and ppi_network can all be tuned as vectors here – every combination gets scored, not just the ones a particular call happens to compare. Additional arguments (e.g. n, the number of PCSF randomized runs) apply uniformly to every build, not gridded.

library(networkGen)
#> 
#> 
library(networkScore)

Kinase-only score

nperms_network is kept small here (2) for a fast-running example; use 50+ for a real analysis. n = 2 likewise trims PCSF’s own randomized-run count per build (default 8) for speed – passed through via ..., uniformly to every build, not gridded. b = 50 clears PCSF’s terminal-inclusion threshold for this data’s percentile-rank-scale prizes (see vignette("networkGen")’s “Key parameters” section for the b/w economics). perc_cutoff and b are both vectors here – every combination is scored, gridded against every condition (not just spec_cutoff/perc_cutoff; rank_uka_abs and ppi_network grid the same way, see above):

respath_kinase <- tempfile("kinase_score_")
dir.create(respath_kinase)

result <- make_golden_score(
  uka = toy_uka,
  spec_cutoff = 1.0,
  perc_cutoff = c(0.5, 0.7),
  ppi_network = ppi_networkv12_502_kins,
  b = c(50, 75),
  respath = respath_kinase,
  nperms_network = 2,
  n = 2
)

Golden score (paired kinase + sensitivity)

The paired path needs a contrast column identifying treatment vs. control (“X vs control” or “control vs X” naming both work), and raw sensitivity data with a matching CELL_LINE_NAME – including a "Control" row, since sensitivity LogFC is computed as fold-change relative to it:

toy_uka_full <- data.frame(
  `x.contrast` = "DrugA vs Control",
  `x.Kinase Name` = real_genes,
  `x.Median Kinase Statistic` = c(2.5, -2.0, 1.8, -1.5, 1.2, -1.0, 0.8, -0.5),
  `x.Mean Specificity Score` = 2.0,
  check.names = FALSE
)

toy_sens <- data.frame(
  CELL_LINE_NAME = rep(c("DrugA", "Control"), each = 4),
  TARGET_1 = rep(real_genes[1:4], 2),
  LN_IC50 = c(-3.5, -1.0, -3.0, -0.8, -1.0, -0.9, -1.0, -0.9)
)

toy_uka_fam <- data.frame(
  Kinase_Name = real_genes,
  Kinase_family = rep(c("FamilyX", "FamilyY"), 4)
)
respath_full <- tempfile("golden_score_")
dir.create(respath_full)

result_full <- make_golden_score(
  uka = toy_uka_full,
  sens = toy_sens,
  control = "Control",
  spec_cutoff = 1.0,
  perc_cutoff = c(0.5, 0.7),
  uka_fam = toy_uka_fam,
  ppi_network = ppi_networkv12_502_kins,
  b = 50,
  respath = respath_full,
  nperms_overlap = 20,
  nperms_network = 2,
  n = 2
)

Reading results

result$results/result_full$results – the main output of this package – has one row per Comparison (the condition/contrast being scored, e.g. "DrugA_vs_DMSO") x every grid parameter, plus the output scores. Only the parameters this particular call actually grids show up as columns – spec_cutoff/perc_cutoff/b/rank_uka_abs/ppi_network each appear only if that dimension has more than one value in this run; a parameter fixed at a single value is dropped, since a constant column carries no information. Lower scores mean more significant throughout.

Golden-score mode (adds sensitivity/target information on top of the kinase-only scores above):

  • score_sig_network – measures whether the top predicted kinases form a more interconnected network with the sensitivity targets than random kinases from the same condition.
  • Overlap scores (obs_overlap/score_sig_overlap) – the overlap between predicted kinases and sensitivity targets, divided by the number of targets. The _fam versions (obs_overlap_fam/score_sig_overlap_fam) are the same comparison at the kinase-family level.

Network-topology metrics behind score_sig_network

Every build – the observed network and every permuted one – gets four topology statistics, written to metrics_observed.csv (one row per condition x metric, from the observed build) and metrics_permutations.csv (one row per condition x metric x permutation):

  • rel_med_path – median shortest-path distance between all node pairs, relative to network size. Smaller means a more compact network.
  • rel_med_path_inv – the same idea, but on an inverse-distance transform of the path lengths first, so close pairs count for more than far-apart ones.
  • density – fraction of all possible edges actually present.
  • clustering – mean local clustering coefficient: how much a node’s neighbors also connect to each other (triangle-forming), averaged across the network.

score_sig_network is a real one-sided permutation p-value on rel_med_path: the fraction of permutations whose rel_med_path is at least as small (compact) as the observed network’s, floored at 1/nperms_network so it’s never exactly 0. score_sig_network_inv is the same test on rel_med_path_inv. density/clustering are recorded for inspection but don’t drive either significance score.

Each (metric, perc_cutoff) combination also gets a diagnostic plot: a histogram of that metric’s permutation values, faceted by condition, with the observed value marked by a red dashed line – a quick visual check of whether the observed network is unusually compact, rather than reading the summary number alone. Output: one folder per grid combination

respath above is just a base directory. Each distinct (spec_cutoff, perc_cutoff, b, rank_uka_abs, ppi_network) combination gets its own folder, same as plain generation with networkGen: the kinase example above grids 2 perc_cutoff values x 2 b values, so 4 folders, each with results.csv/metrics_permutations.csv/metrics_observed.csv, the faceted diagnostic histograms (Network_metrics_plots/<metric>_cutoff<cutoff>.png – permutation-null- distribution per metric, faceted by condition, observed value marked with a line), and each condition’s observed network (nodes/edges/wc_df CSVs). Permutation networks (there are nperms_network of them per condition) are never written – only the observed build:

Comparing scores across separate runs

plot_score_comparison() reads every results.csv under each of several result folders (recursively – so a folder can be a single grid combination, or a whole multi-combination run) and plots score_sig_network/score_sig_network_inv as boxplots per Comparison, one facet per folder – for comparing the same comparisons across different grid combinations, or entirely separate runs. Give each folder an alias; that alias becomes its facet title, and facets appear in the order given, not alphabetically. A box’s spread comes from however many grid combinations exist inside that folder – a single-combination folder gives a one-point “box”.

Safety guard for large grids

Like networkGen::run_network_grid(), both functions refuse to proceed (without building anything) if the grid – with permutations included – would exceed max_tasks (default 500) networks:

make_golden_score_kinase(
  uka = toy_uka, spec_cutoff = 1.0, perc_cutoff = c(0.5, 0.7),
  ppi_network = ppi_networkv12_502_kins, b = 50, respath = respath_kinase,
  nperms_network = 50, max_tasks = 10
)
#> Grid has 4 condition x spec_cutoff x perc_cutoff x b x rank_uka_abs x ppi_network cells
#> Error:
#> ! make_golden_score_kinase() would build 204 networks (4 grid cells x (1 observed + 50 permutations)), over max_tasks = 10. Review the grid before proceeding, or pass a higher max_tasks explicitly if this size is actually intended.

Parallel vs. sequential execution

Every network needed – one observed plus nperms_network permuted, for every condition x spec_cutoff x perc_cutoff x b x rank_uka_abs x ppi_network combination – is submitted together, so a future plan set before calling parallelizes across all of it (every condition and every permutation at once, not just across conditions):

future::plan(future::multisession, workers = 4)

Without a plan set, both functions run sequentially – still correct, just not parallel.
